## Context
- This project uses a monorepo architecture managed by Nx. Path aliases are mapped in the root tsconfig.base.json or individual project configurations to enforce strict module boundaries between different projects and libraries. Within an individual project or package, standard relative directory traversal is maintained to reflect local codebase hierarchy.

## Requirements
- Internal Scope (Relative Paths): When importing modules, components, utilities, or types that reside within the same project/package, you must use standard relative paths (./, ../, ../../). Do not use workspace aliases for internal package files.

- External Scope & Nx Libs (Mandatory Alias Usage): When importing code across project boundaries—such as external shared libraries, or any lib generated by Nx—you must use the defined Nx workspace aliases (e.g., @workspace/shared/types, @my-app/components).

- Strict Boundary Enforcement: Deep-linking into another library's internal source tree is strictly prohibited. External code must only be accessed via the library's official entrypoint (the index file mapped in the paths config).

## Execution Protocol for the Agent
- Analyze Project Boundaries First: Before generating or modifying any import statement, determine whether the target file resides within the same local package/project or in an external Nx library.

- Apply Scope-Based Import Rules:

   - Inside same package: Resolve the import using standard relative path climbing (../).

   - Across packages/libs: Inspect tsconfig.base.json to read the defined "paths" configuration and map the import strictly to the matching workspace alias.

- Refuse Incorrect Refactoring: If an automated auto-import snippet attempts to use an alias for a local file, or conversely, tries to use a long relative path (../../../../libs/...) to reach into another Nx lib, you must immediately rewrite it to comply with the boundaries defined above.
